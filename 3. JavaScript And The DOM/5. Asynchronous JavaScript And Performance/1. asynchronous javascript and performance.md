## Event Loop
Javascript is single-threaded, means JavaScript can only do one thing at a time. Each time a function is called, JavaScript puts that function at the top of the call stack. JavaScript will work through the call stack from top to bottom until the stack is empty. Because of this any long running task can block the remaining code to be executed. Like event listeners dont really finish their job, event listeners have to constantly listen or else they can't respond to any interactions. They don't stop listening until you remove them. That function keeps running. But, remember that .addEventListener() is a method of the DOM. So when you create an event listener, it gets pushed to the Web APIs provided by your browser. And your browser can handle multiple listeners without problems. So functions that we define in our JavaScript are handled by the call stack. Functions that are part of the Web API in the browser are handled there. 


### Task Queue
![call stack](https://github.com/user-attachments/assets/61b5a816-9ab5-4527-87d1-ecd3aef40835)

When our event listener registers an event and executes the callback, it actually sends that to another spot in our loop called the task queue, it's an intermediate step between the web API and the call stack. When our web API calls the callback function and it goes into the task queue. When a function makes its way into the task queue, it has to wait until the call stack is completely empty. Any functions patiently waiting in the task queue will keep waiting until the call stack has finished with all the functions currently in the call stack. Once all the functions in the call stack are complete, then the function in the task queue moves into the call stack so our JavaScript can execute the code. Blocking code can be an issue here as well, you can have event listeners throwing all sorts of handlers into the task queue. But if there's a function still running, those event handlers will never go into call stack and you'll end up with an completely unresponsive site.



## Promises
Promises are basically an agreement between you and JavaScript. You tell your program you want something to happen, and JavaScript promises it will complete that thing you want. That doesn't mean it will be successful, but you've gotten a promise from JavaScript that it's going to finish it. That promise will either return a
- **`resolve()`** operation for success and this captured with `.then()` method.
- **`reject()`** operation for failure and this captured with `.catch()` method.

Both `.then()` and `.catch()` take callbacks as their arguments. So when either method is called, their callbacks run.
```
new Promise ((resolve, reject) => {
const success = true; //this would be a successful result of your operation
if (success) { 
	resolve();
} else {
	reject();
	}
})
.then(() => console.log('successful')) 
.catch(() => console.log('error'))
```
Since we've set the value of success to 'true,' the `resolve()` operation will run. That gets captured by the `.then()` method and the result will be 'successful' logged in to the console.


### Microtask Queue
Promises are asynchronous, that mean that Promises are handled somewhere else since the call stack is single threaded and synchronous. Means your `.then()` and `.catch()` methods are sent to the `microtask queue` when the promise resolves. Microtask queue takes priority over the task queue. So once the call stack is empty, the event loop checks the microtask queue and clears it before pulling anything out of the task queue.



## Fetch
`fetch()` is actually part of the Web API from the browser. So when a fetch request is added to the call stack it's taken off the call stack and pushed into the Web API part of the event loop. This means that fetch is non-blocking and the rest of your code can continue running.
```
fetch('https://yourAPIEndpoint.com')
	.then(console.log('successful')
	.catch(console.log('error')
```
Once fetch is in the Web API, it immediately returns a Promise. This happens before the result is even returned. So `fetch()` hands off handling the result of the fetch request to the Promise handler. Since it returns a Promise, we know that the resolution of the Promise, `.then()` or `.catch()` will go to the microtask queue. So when the fetch completes, our then or catch methods pass their callbacks into the microtask queue based on their success or failure of our fetch operation. So if there's nothing in the call stack, our resolution will be handled before any of our events in the task queue. This is great in that our fetch request doesn't cause any blocking code since it ends up in the Web API and eventually the Promise handler. But this can cause a problem if we depend on our fetch request to populate our DOM.
```
let userData
fetch('https://myEndPoint.com')
	.then(response => response.json())
	.then((data) => {
		userData = data;
		})
const newElement = document.createElement('p')
newElement.textContent = userData.bio // throws a TypeError
```
The problem is that immediately after our fetch request is made, it's handed off to the web API so it doesn't block our code, which is great.  But in this case we're trying to create elements with userData, which hasn't been populated yet. Since the fetch request is asynchronous and hasn't finished yet, userData is still empty and the result is an error. So in this case the asynchronous nature of fetch requests can actually hurt what we're trying to do.



## Async/Await
```
async function fetchData() { … }
const fetchData = async() => { … }
```
`async` tells JavaScript that your function will have some asynchronous components in it. `async` functions themselves will return a Promise. So when the function is complete, its return is essentially the same thing as the `resolve()` of a Promise. By putting the `await` keyword before a Promise, like a Promise returned from a fetch operation, you're telling JavaScript to pause the execution of the rest of the function until the Promise is resolved. Using `await` we dont have to use `.then()` method.
```
const fetchUserData = async() => {
	const responseData = await fetch('https://whateverAPIEndpoint.com')
	const userData = await responseData.json()
	const newElement = document.createElement('p')
	newElement.textContent = userData.bio 
}
```



## Try/Catch Block
Within `try` block we will write the code that we want to execute and if an error happens in your `try` block, the `catch` block will capture that error and execute the code. The only way the fetch Promise will reject is if there's an network error or for some reason the request can't be made. Even if there's a problem with the fetch and it doesn't return as expected, the `catch` block won't catch that error because the Promise still resolves and sends a `response` object. `response` object from fetch includes an `.ok` property that's a simple `boolean`.  We can add a conditional in our code that checks if the `response.ok` prtoperty is `true`. If it's `false` we can manually throw an error that will stop our function in its tracks and pass control over to the `catch` block. 
```
const fetchUserData = async() => {
	try {
		const responseData = await fetch('https://myEndPoint.com')
		if (!responseData.ok) {
			throw new Error('Error fetching data: ${responseData.status}, ${responseData.statusText')
		}
		const userData = await responseData.json()
		const newElement = document.createElement('p')
		newElement.textContent = userData.bio 
	} catch(error) {
		console.log(error)
	}
}
```
