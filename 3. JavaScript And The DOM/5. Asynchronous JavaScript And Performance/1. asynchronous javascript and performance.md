## Event Loop
Javascript is single-threaded, means JavaScript can only do one thing at a time. Each time a function is called, JavaScript puts that function at the top of the call stack. JavaScript will work through the call stack from top to bottom until the stack is empty. Because of this any long running task can block the remaining code to be executed. Like event listeners dont really finish their job, event listeners have to constantly listen or else they can't respond to any interactions. They don't stop listening until you remove them. That function keeps running. But, remember that .addEventListener() is a method of the DOM. So when you create an event listener, it gets pushed to the Web APIs provided by your browser. And your browser can handle multiple listeners without problems. So functions that we define in our JavaScript are handled by the call stack. Functions that are part of the Web API in the browser are handled there. 


### Task Queue
![call stack](https://github.com/user-attachments/assets/61b5a816-9ab5-4527-87d1-ecd3aef40835)

When our event listener registers an event and executes the callback, it actually sends that to another spot in our loop called the task queue, it's an intermediate step between the web API and the call stack. When our web API calls the callback function and it goes into the task queue. When a function makes its way into the task queue, it has to wait until the call stack is completely empty. Any functions patiently waiting in the task queue will keep waiting until the call stack has finished with all the functions currently in the call stack. Once all the functions in the call stack are complete, then the function in the task queue moves into the call stack so our JavaScript can execute the code. Blocking code can be an issue here as well, you can have event listeners throwing all sorts of handlers into the task queue. But if there's a function still running, those event handlers will never go into call stack and you'll end up with an completely unresponsive site.



## Promises
Promises are basically an agreement between you and JavaScript. You tell your program you want something to happen, and JavaScript promises it will complete that thing you want. That doesn't mean it will be successful, but you've gotten a promise from JavaScript that it's going to finish it. That promise will either return a
- **`resolve()`** operation for success and this captured with `.then()` method.
- **`reject()`** operation for failure and this captured with `.catch()` method.

Both `.then()` and `.catch()` take callbacks as their arguments. So when either method is called, their callbacks run.
```
new Promise ((resolve, reject) => {
const success = true; //this would be a successful result of your operation
if (success) { 
	resolve();
} else {
	reject();
	}
})
.then(() => console.log('successful')) 
.catch(() => console.log('error'))
```
Since we've set the value of success to 'true,' the `resolve()` operation will run. That gets captured by the `.then()` method and the result will be 'successful' logged in to the console.


### Microtask Queue
Promises are asynchronous, that mean that Promises are handled somewhere else since the call stack is single threaded and synchronous. Means your `.then()` and `.catch()` methods are sent to the `microtask queue` when the promise resolves. Microtask queue takes priority over the task queue. So once the call stack is empty, the event loop checks the microtask queue and clears it before pulling anything out of the task queue.



## Fetch
`fetch()` is actually part of the Web API from the browser. So when a fetch request is added to the call stack it's taken off the call stack and pushed into the Web API part of the event loop. This means that fetch is non-blocking and the rest of your code can continue running.
```
fetch('https://yourAPIEndpoint.com')
	.then(console.log('successful')
	.catch(console.log('error')
```
Once fetch is in the Web API, it immediately returns a Promise. This happens before the result is even returned. So `fetch()` hands off handling the result of the fetch request to the Promise handler. Since it returns a Promise, we know that the resolution of the Promise, `.then()` or `.catch()` will go to the microtask queue. So when the fetch completes, our then or catch methods pass their callbacks into the microtask queue based on their success or failure of our fetch operation. So if there's nothing in the call stack, our resolution will be handled before any of our events in the task queue. This is great in that our fetch request doesn't cause any blocking code since it ends up in the Web API and eventually the Promise handler. But this can cause a problem if we depend on our fetch request to populate our DOM.
```
let userData
fetch('https://myEndPoint.com')
	.then(response => response.json())
	.then((data) => {
		userData = data;
		})
const newElement = document.createElement('p')
newElement.textContent = userData.bio // throws a TypeError
```
The problem is that immediately after our fetch request is made, it's handed off to the web API so it doesn't block our code, which is great.  But in this case we're trying to create elements with userData, which hasn't been populated yet. Since the fetch request is asynchronous and hasn't finished yet, userData is still empty and the result is an error. So in this case the asynchronous nature of fetch requests can actually hurt what we're trying to do.



## Async/Await
```
async function fetchData() { … }
const fetchData = async() => { … }
```
`async` tells JavaScript that your function will have some asynchronous components in it. `async` functions themselves will return a Promise. So when the function is complete, its return is essentially the same thing as the `resolve()` of a Promise. By putting the `await` keyword before a Promise, like a Promise returned from a fetch operation, you're telling JavaScript to pause the execution of the rest of the function until the Promise is resolved. Using `await` we dont have to use `.then()` method.
```
const fetchUserData = async() => {
	const responseData = await fetch('https://whateverAPIEndpoint.com')
	const userData = await responseData.json()
	const newElement = document.createElement('p')
	newElement.textContent = userData.bio 
}
```



## Try/Catch Block
Within `try` block we will write the code that we want to execute and if an error happens in your `try` block, the `catch` block will capture that error and execute the code. The only way the fetch Promise will reject is if there's an network error or for some reason the request can't be made. Even if there's a problem with the fetch and it doesn't return as expected, the `catch` block won't catch that error because the Promise still resolves and sends a `response` object. `response` object from fetch includes an `.ok` property that's a simple `boolean`.  We can add a conditional in our code that checks if the `response.ok` prtoperty is `true`. If it's `false` we can manually throw an error that will stop our function in its tracks and pass control over to the `catch` block. 
```
const fetchUserData = async() => {
	try {
		const responseData = await fetch('https://myEndPoint.com')
		if (!responseData.ok) {
			throw new Error('Error fetching data: ${responseData.status}, ${responseData.statusText')
		}
		const userData = await responseData.json()
		const newElement = document.createElement('p')
		newElement.textContent = userData.bio 
	} catch(error) {
		console.log(error)
	}
}
```



## Layout Shift
Layout shift is that noticeable change in the size and position of elements when things are loaded into the DOM. We've all seen it before, usually when an advertisement loads in after the page is finished and suddenly article moves three paragraphs down or worse, it shifts the layout right as you're about to click a link and you accidentally click on one of those ads. It's so bad it's even measured as part of **Google's Core Web Vitals** that are used to rank sites. It's called Cumulative Layout Shift or `CLS`. To avoid layout shift we can loader or placeholder for each part of the layout. You can also make full-page placeholders called skeletons that can illustrate where the final updated updated elements will go. These can be animated too so that your whole page looks dynamic even while it's simply waiting for data.
```
const fetchUserData = async() => {
	try {
		const loadingElement = document.querySelector('.loadingIndicator')
		const elementToModify = document.querySelector('.modify')
		const responseData = await fetch('https://whateverAPIendPoint.com')
		if (!responseData.ok) {
			throw new Error('Error fetching data: ${responseData.status}, ${responseData.statusText')
		}

		// DOM modifications
		loadingElement.style.display='none'
		elementToModify.append(DOM modifications)
	} catch(error) {
		console.log(error)
	}
}
```



## Optimize API Request
When we rely on data from external API, then its really important to optimize the API calls, for faster loading of data and reducing related cost. Cost can be because of DB access or API requests. Following are some options for optimizing this


### Global Variable
One simple way is to create a variable at the root of your code and store the result of your fetch operation in it. Since that variable's at the root level of your code, it almost acts like a global variable and can be used in all your functions without having to make another fetch request. But be careful of large data sets. You don't want to expend a ton of memory storing data you don't really need.
```
let userData
const fetchUserData = async () => {
    const rawUserData = await fetch('./data/projectsData.json');        
    userData = await rawProjectData.json();
}
```


### Caching
By default, fetch requests have a built in cache. When you make a request, fetch stores the response in its own cache. If you make the same request twice, fetch will check to see if a response already exists in its cache and is fresh. If so, then it will use that response. If it's a stale response or there isn't a response, it will make a request and update the cache with the received data. This default caching is great, but you can make adjustments by passing in cache values in your fetch request. You can also values like `force-cache` that can change that behavior. `force-cache` will use the existing cache no matter what, even if it's a stale response. This can be great if you don't expect your data to change much and it's all handled by your fetch request.
```
const fetchUserData = async () => {
    const rawUserData = await fetch('./data/projectsData.json', { cache: "force-cache" })        
    userData = await rawProjectData.json();
}
```
The data fetched using the Fetch API is stored in the browser's cache. This cache is managed by the browser and is separate from your application's memory or local storage. The browser determines how long to keep the cached data based on HTTP headers like `Cache-Control` and `Expires`. Browsers use several mechanisms to determine whether cached data is expired or still valid. 

- The **`Cache-Control`** header is a directive used by the server to specify caching policies. It can include various directives, such as:
	- **`max-age`**: Specifies the maximum amount of time (in seconds) that the resource is considered fresh. For example, Cache-Control: max-age=3600 means the resource is fresh for one hour.
	- **`no-cache`**: Indicates that the resource must be revalidated with the server before being used.
	- **`no-store`**: Instructs the browser not to cache the resource at all.
	- **`public/private`**: Indicates whether the response can be cached by any cache or only by the user's browser.

-  The **`Expires`** header provides an absolute date and time after which the resource is considered stale. For example, `Expires: Wed, 21 Oct 2023 07:28:00 GMT` indicates that the resource is valid until that specific date and time.

-  **Last-Modified**: This header indicates the last time the resource was modified. The browser can use this information to determine if it should re-fetch the resource.

- **ETag**: This is a unique identifier assigned by the server to a specific version of a resource. The browser can send this identifier back to the server in a conditional request to check if the resource has changed.

- **Revalidation**: When a cached resource is considered stale (either due to `max-age`, `Expires`, or other conditions), the browser may perform a revalidation request to the server. This involves sending a request with the `If-Modified-Since` header (using the `Last-Modified` date) or the `If-None-Match` header (using the `ETag`). If the resource has not changed, the server responds with a `304 Not Modified` status, and the browser can continue using the cached version.


### Local Storage
You can save the results of your fetch request in local storage where you can have easy access to all the data you need. Local storage only takes strings so you do have to convert objects using `JSON.stringify()`. The nice thing about this is that it can persist across page reloads without having another network request. Just check to see if it exists before performing your fetch operation. Remember that you have to `.parse()` the local storage first since it's saved as a string. 
```
let userData

const fetchUserData = async () => {
    const savedData = JSON.parse(localStorage.getItem('userData'));
    if (savedData && savedData.length > 0) {
        userData = savedData
    } else {
        const rawUserData = await fetch('./data/projectsData.json', { cache: "force-cache" })        
        userData = await rawProjectData.json();
        localStorage.setItem('userData', JSON.stringify(userData))
    }
}
```
The data is stored in the browser's local storage, which is a part of the Web Storage API. Each web browser (like Chrome, Firefox, Safari, etc.) has its own implementation of local storage, and the data is specific to the domain that created it. Data stored in `localStorage` persists even after the user closes the browser or navigates away from the page. It remains available until it is explicitly deleted by the application or the user (e.g., through browser settings). Data in `localStorage` is stored as key-value pairs. Most browsers impose a storage limit on `localStorage`, typically around `5-10 MB` per origin (domain). This limit can vary between browsers, so it's important to be mindful of the amount of data you store.
```
localStorage.setItem('key', 'value');
const value = localStorage.getItem('key');
localStorage.removeItem('key');
localStorage.clear();
```


### IndexedDB
If you have a much larger dataset or you need your application to work even without a network, You can use indexedDB to store data in your browser's own database. Of course It's also much more complex than the other options and you have to make sure you have good data handling. If you want your indexedDB data to match your online database, you have to have some way of syncing your databases once you do have connection.
