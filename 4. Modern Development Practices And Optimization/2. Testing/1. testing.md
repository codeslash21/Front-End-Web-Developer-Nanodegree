## Testing
**Continuous Integration (CI)** is the process of regularly pushing development code into the shared repository. It involves running the build process to ensure it completes successfully, followed by automated tests to verify the program functions as expected. Once this is done, **Continuous Delivery (CD)** or Continuous Deployment can begin, which involves pushing the code to a deployment environment or directly to production.


### Types of Testing
- **Manual Testing:** This include testing features manually, by simulating user interaction and running different test cases manually, SOme organisation has QA team for this.
- **Automated Testing:** Run different types of tests automatically, for example running unit test, integration test, end-to-end test, regression test one after another in a pipeline. Often this automated testing is part of CI/CD pipeline. Primary purpose of the automated testing is to ensure code quality and minimize the number of issues and bugs in the production. There are many types of automated testing. Here are a few key ones to get you started:
  - **Unit Tests:** Break the application into small modules or units that can be tested in isolation.
  - **Integration Tests:** Verify that multiple components of a system work together correctly.
  - **Regression Tests:** Ensure that changes to the application do not break any existing features.
  - **End-to-End Tests:** Test the application as a whole by simulating real-world scenarios users would encounter.
  - **Functional Testing:** Focuses on the application's usability and ensures that features function as expected.
  - **Performance Testing:** Verifies that the application performs well under various conditions and situations.


### Testing Terms
- **Test Case:** A specific block of code dedicated to a single test. It can be considered a set of instructions performed by the test itself.
- **Test Suite:** A collection of multiple test cases grouped together.
- **Assertion:** Typically the final part of a test where we validate the result and check for expected behavior. For example, "If the function does X, it should return Y."
- **Test Environment:** A separate environment where tests are run. It is distinct from the production environment and includes tools required to execute tests.
- **Happy Path:** Testing ideal behaviors or conditions. This involves testing what should "typically" happen when a user interacts with the application or when a function receives the expected input.
- **Edge Case:** Testing unexpected behavior to catch unusual or incorrect inputs. This helps identify potential issues, such as users performing unintended actions or developers accidentally passing incorrect data types to a function.



## Unit Testing With Mocha
Mocha is a JavaScript testing framework that runs in both the browser and Node.js, making it ideal for both unit and integration tests. When Mocha tests are run, they execute within the **Mocha test runner environment**. To run tests, Mocha requires them to be in a file ending with `.test.js`, such as `mytest.test.js`, which is typically kept in a `test` folder. Each test includes a **describe** block to define a test suite and an **it** block to define a test case. Mocha offers many additional features, including functions to execute blocks of code before and after test suites, specialized functionality to handle asynchronous methods, and much more.

#### Describe Block:
- A function that takes two arguments:
- A string describing the test suite.
- A callback function that contains all the test cases for the suite.

#### It Block:
- Similar to a describe block, it takes two arguments:
- A string describing the test case.
- A callback function that contains the test logic. The callback in an it block is where the main logic resides. It includes:
- Setting up the test, such as calling the code being tested and preparing any arguments or mock data.
- An assertion, which verifies the test results to ensure the code behaves as expected.


### Chai
Mocha comes with some built-in assertion methods, but we can use an assertion library like `Chai` to expand functionality. Chai provides methods like `expect` and `should` that allow us to chain other methods and create more specific assertions. In this example below, we use `expect`, `to`, and `equal` to assert that the `result` variable is expected to equal `10`: `expect(result).to.equal(10)`. In one `it` block we can have multiple `expect` statement. The test suite below tests a function that validates user input for a password. The password must be at least 12 characters long and contain special characters. To run the tests run `mocha` command in the terminal.
```
const { expect } = require("chai");
// Mocha is a test runner and does not need to be imported.

describe("Password Validator", () => {
    it("should return true for a valid password", () => {
      const validPassword = "StrongPass123!";
      expect(passwordValidator(validPassword)).to.be.true;
    });

    it("should return false for a password shorter than 12 characters", () => {
      const shortPassword = "Short1!";
      expect(passwordValidator(shortPassword)).to.be.false;
    });

    it("should return false for a password without a special character", () => {
      const noSpecialChar = "NoSpecialChar123";
      expect(passwordValidator(noSpecialChar)).to.be.false;
    });

    it("should return false for an empty password", () => {
      const emptyPassword = "";
      expect(passwordValidator(emptyPassword)).to.be.false;
    });
});
```
