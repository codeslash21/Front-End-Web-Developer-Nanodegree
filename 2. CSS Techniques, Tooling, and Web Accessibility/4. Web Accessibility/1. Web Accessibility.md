## Web Accessibility
One of the first steps to making your application more accessible is using Semantic HTML. Semantic HTML helps describe the structure and purpose of a webpage to assistive tools like screen readers. Tags like `<div>` and `<span>` are generic and don’t provide much information about an element's purpose. In contrast, semantic tags like headings (`<h1>`, `<h2>`, etc.) help identify specific sections of a page, making it easier to navigate.


### Examples of Semantic Tags:
- `<main>`: Identifies the main content of the page.
- `<nav>`: Used for navigation menus.
- `<aside>`: Represents supporting information, such as sidebars or advertisements.
- `<footer>`: Indicates the end of the page and may contain content like sitemaps, contact information, or copyright notices.


### ARIA Attributes
ARIA(Accessibility Reach Internet Application) attributes are another way to help identify the purpose of different HTML elements. Modern applications often rely on a combination of ARIA attributes and Semantic HTML, or sometimes Semantic HTML alone.

#### ARIA Attributes includes:
- **Roles:** `role` attribute is used to define the purpose of an element, such as `button` or `menu`.
- **Properties:** Describe characteristics of an element, like `aria-label` or `aria-hidden`.
- **States:** Describe dynamic properties of an element that can change, such as `aria-expanded` or `aria-checked`.



## WCAG
The Web Content Accessibility Guidelines (WCAG) 2 are the go-to standards for making web content accessible. By following these guidelines, we can make sure our applications are as accessible as possible for as many people as possible. The Web Content Accessibility Guidelines (WCAG) are designed to make digital content accessible for people with disabilities. There are three levels of compliance: **A**, **AA**, and **AAA**.


### Level A Compliance Examples
- **1.1.1 Non-text Content**: Provide text alternatives for all non-text content (e.g., alt text for images).
- **1.3.2 Info and Relationships**: Structure (like headings, lists, etc.) must be programmatically determined or available in text.
- **1.4.1 Use of Color**: Don’t rely on color alone to convey information (e.g., use more than just red to indicate errors).


### Level AA Compliance Examples
- **1.2.4 Captions (Live)**: Captions must be provided for live audio (like webinars or live streams).
- **2.4.5 Multiple Ways**: Offer more than one way to find a page (search bars, navigation menus, sitemaps, etc.).
- **3.3.3 Error Suggestions**: Help users fix input errors by providing clear suggestions (e.g., "Email must include @").


### Level AAA Compliance Examples
- **1.2.6 Sign Language (Prerecorded)**: Add synchronized sign language interpretation to prerecorded videos.
- **1.4.7 Low or No Background Audio**: Either remove background audio or give users the option to turn it off.
- **2.3.2 Three Flashes**: No element should flash more than three times in one second (important for preventing seizures).



## Verifying Accessibility
### Manual Testing
**Chrome DevTools** provides tools for emulating system settings. Testing your application manually using these tools is always a great starting point to identify potential issues.


### Automated Accessibility Checkers
There are several online tools that can automatically check your application for accessibility issues. The tool will run automated checks and generate a report highlighting compliance issues and suggestions for improvement. The **W3C Web Accessibility Evaluation Tools List** is an excellent resource for finding tools to validate your accessibility efforts. It includes a wide variety of options to help you test and refine your application’s accessibility.These tools typically allow you to:
- Provide a link to your deployed application.
- Upload documents.
- Submit code snippets.


### Screen Readers
Another great way to verify the accessibility of your application is by testing it with the tools people will actually use. Both macOS and Windows come with built-in screen readers that you can use to ensure your application is parsed correctly and functions as intended with these tools.
