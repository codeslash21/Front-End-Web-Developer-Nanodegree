## CSS Preprocessor
A CSS preprocessor is a tool which enhances the capabilities of regular CSS, offering advanced features that simplify and improve your workflow. With preprocessors, developers can write code in a more structured and efficient way, using features like **variables**, **nesting**, and **mixins**, which are then compiled into standard CSS that browsers can interpret. While some of these features, such as variables and nesting, are now available in standard CSS, preprocessors still offer unique advantages. For example, preprocessor variables are more powerful as they allow calculations and can be used in older browsers. Preprocessor nesting syntax also enables deeper organizational flexibility that CSS alone does not yet fully replicate.


### Commonly Used Preprocessors
While there are several preprocessors available, the most widely used ones are:
- **Sass**: Known for its rich feature set and ease of use.
- **Less**: Similar to Sass but with a slightly different syntax.
- **Stylus**: Offers more flexibility in syntax but is less common.


### Purpose
- **Improved Readability**: Features like nesting and variables make your stylesheets easier to understand and maintain
- **Modularity**: Preprocessors allow you to split your CSS into multiple files, making it easier to organize and manage large projects
- **Consistency**: Variables and mixins ensure uniform styles across your project
- **Efficiency**: Reduces repetitive tasks and boilerplate code, giving you more time to focus on functionality and user experience


### Sass VS CSS
- Sass nesting is compiled to flat css, so its supoorted by all browsers (after compilation). But, for CSS nesting no compilation is done, so only the modern browsers can understand. Because of the same reason, media query nesting in css is only supported in modern browser.
- Sass Variables evaluated at compile time, exist only while building CSS, and browser never sees them. Sass Variables are lexical scope, do not inherit and block-based. Sass variables are replaced before your CSS is generated, they do not exist in the final CSS and they cannot be changed at runtime.Variables are valid only within the file or block where they are defined, no global access unless imported. This is best for consistent colors, spacing, fonts calculations, mixins and functions, build-time theming. This can not be change based on user interaction or based on dark/light theme toggles (without recompiling), also cant be accessed in JavaScript.
- CSS Variables are DOM-based scope, inherit automatically, cascade like normal CSS. Css custom variables remain in the browser and they can be changed dynamically without recompiling CSS. Its inherited through the cascade, a variable defined in a parent affects children. Css variables are great for themes, user interaction, realtime updates, dynamic styling. It can not perform calculations before rendering. There is runtime overhead invloved, compared to this sass variables are faster as they precompiled. Css variables can change dynamically via JavaScript, media queries, pseudo-classes.
```
// sass
$color: red;
.card {
  $color: blue;
  color: $color; // blue
}
.button {
  color: $color; // red
}
```
```
// css
:root {
  --color: red;
}
.card {
  --color: blue;
}
.card p {
  color: var(--color); /* blue */
}
```
- CSS variables are better for math when values need to change dynamically at runtime, such as responsive layouts or theming, while Sass variables are better for static, compile-time calculations where performance and browser compatibility matter. Also, if you need to apply loop (for/while) or logic (if) then sass variables are better choice.
```
// sass, not possible in css
@for $i from 1 through 5 {
  .m-#{$i} {
    margin: $i * 8px;
  }
}
```
- `calc()` method is required for css variables, but not required for sass variables
```
// css
:root {
  --gap: 16px;
}
.box {
  margin: calc(var(--gap) * 2);

// sass
$gap: 16px;
.box {
  margin: $gap * 2;
}
```

- If you have `main.css` that imports `header.css`, `footer.css`, and `sidebar.css`, the browser has to make four separate requests to the server. This slows down your page because the browser has to stop and fetch each file one by one. But, sass compiles(combines) them into one single `.css` file before it ever reaches the server.
- Custom function is not supported in css, browser cant execute logic. But, sass supports custom function and function runs at compile time and output of the function is static css.
```
@function theme-color($theme) {
  @if $theme == dark {
    @return #000;
  } @else {
    @return #fff;
  }
}
body {
  background: theme-color(dark);
}
```
- CSS variables have runtime overhead, because they are dynamic, the browser must recalculate values while the page is running. For the following example, the browser must find the value of `--space` by traversing up the DOM tree (because CSS variables inherit), then resolve `var(--space)` and evaluate `calc()`. And finally, recompute styles if the variable changes and possibly trigger layout or paint. The browser tracks CSS variable changes through its style system and marks affected elements as “dirty” when a custom property value changes, triggering style recalculation.
```
.card {
  padding: calc(var(--space) * 2);
}
```


### Preprocessors And CSS Methodologies
Preprocessors work seamlessly with methodologies like BEM and SMACSS. With **BEM**, **Nesting** reduces the repetition often found in BEM class names Example :
```
.button {
    &__label {               
       font-size: 16px;
    }
    &--primary {               
       background-color: $primary-color;
       color: white;
    }
}
```
With **SMACSS**, Modular files align naturally with SMACSS categories (e.g., base, layout, modules) Example File Structure :
```
styles/
├── base/_reset.scss
├── layout/_header.scss
├── modules/_button.scss
├── state/_is-hidden.scss
├── theme/_dark-mode.scss
```



## Sass
**Sass**, short for **Syntactically Awesome Stylesheets**, is a CSS preprocessor which enhances the way developers write styles. As browsers can only interpret CSS, developers write their styles in Sass using a more advanced syntax, which is then compiled into standard CSS files. Sass provides two syntax options:

- **SCSS (Sassy CSS)**: A syntax that closely resembles traditional CSS, using `{}` and `;`. SCSS is the more popular syntax due to its familiarity and flexibility.
- **Sass**: An older syntax that relies on indentation and newlines instead of braces and semicolons. While still supported, it’s less commonly used today.

Sass files must be saved with the `.scss` or `.sass` extension, which then need to be compiled into standard `.css` files. This compilation process ensures your Sass code can be read by browsers. Modern tools, such as a Live Sass compiler in VS Code, automate this workflow, making the transition from Sass to CSS seamless.


### Key Features
### Nesting
Nesting allows you to write styles that reflect the structure of your HTML. This eliminates the need to repeat parent selectors, making your code more concise and easier to read.

#### Styles in CSS:
```
.nav {
  background-color: #f8f9fa;
}
.nav li {
  margin: 5px 0;
}
.nav li a {
  text-decoration: none;
  color: #007BFF;
}
```

#### Styles using SCSS:
```
.nav {
  background-color: #f8f9fa;

  li {
    margin: 5px 0;

    a {
      text-decoration: none;
      color: $primary-color;
    }
  }
}
```

#### Parent Selector
The `&` symbol, known as the **parent selector**, is a Sass feature which references the current parent selector. This is particularly useful for stateful or modified versions of a component.
```
.button {
  padding: 10px;
  background-color: $primary-color;
  &:hover {
    background-color: darken($primary-color, 10%);
  }
  &--large {
    padding: 20px;
  }
}
```


### Compiling Sass
Because browsers can only read CSS, your Sass files need to be compiled. This process transforms your `.scss` files into standard `.css` files. Once compiled, your SCSS code becomes browser-ready CSS, seamlessly integrating into your project. Popular tools for compilation include:
- **VS Code extensions**: Tools like **Live Sass Compiler** make it easy to compile SCSS files in real time
- **Command-line tools**: For developers who prefer terminal workflows, the **Sass CLI** provides an efficient way to compile files


### Variables
- **Maintainability**: By defining values in one place, you can update them globally with a single change.
- **Consistency**: Variables ensure uniform styling for common elements like brand colours or typography.
- **Efficiency**: Reduces repetitive typing and speeds up production time.
```
//_variables.scss
$primary-color: #4CAF50;
$secondary-color: #FFC107;
$font-primary: 'Roboto', sans-serif;
```
```
//styles.scss
.button {
    background-color: $primary-color;
    color: white;
    font-family: $font-primary;
}
```


### Partials
- **Organization**: Keeps styles modular and prevents large, unwieldy CSS files
- **Scalability**: Easier to manage styles for growing projects by focusing on small, reusable pieces
- **Reusability**: Components or patterns can be isolated for use across multiple projects

Partial files are named with a leading underscore (e.g., `_header.scss`), signaling to the compiler that they should not generate their own CSS file. Instead, partials are imported into a main Sass file using the **@use** keyword. Example Folder Structure :
```
scss/
   styles.scss
   partials/
        _variables.scss
        _header.scss
        _buttons.scss
```
```
// import into style.scss
@use 'partials/variables';
@use 'partials/header';
@use 'partials/buttons';
```


### Mixins
**mixins** are reusable blocks of CSS that can accept arguments (variables) to introduce dynamic behavior. By defining a mixin once, you can apply it across your stylesheets wherever needed, reducing redundancy and improving consistency. Mixins can:
- Accept multiple parameters to dynamically alter styles.
- Incorporate calculations and logic to handle complex requirements.
- Combine with other Sass features like variables and nesting for powerful results.

### Why Use Mixins
- **Reusability**: Write once, reuse multiple times across components
- **Consistency**: Maintain uniform styles for similar elements
- **Flexibility**: Customize styles dynamically using parameters
- **Scalability**: Simplify updates by centralizing reusable logic


#### Basic Styling
```
//_mixins.scss
@mixin fontStyle($size, $weight: bold, $color: #333) {
      font-size: $size;
      font-weight: $weight;
      color: $color;
}
```
```
//styles.scss
h1 {
       @include fontStyle(32px, bold, #007BFF);
}
```

#### Responsiveness
```
//_responsive.scss
@mixin responsivePadding($padding) {
     padding: $padding;
     @media (min-width: 768px) {
         padding: $padding * 1.5;
     }
}
```
```
// style.scss
.card {
    @include responsivePadding(10px);
}
```
```
// compiled css
.card {
    padding: 10px;
}
@media (min-width: 768px) {
    .card {
        padding: 15px;
    }
}
```

#### Using Logic
```
//_button.scss
@mixin buttonStyle($type) {
    @if $type == 'primary' {
        background-color: #007BFF;
        color: white;
    } @else if $type == 'secondary' {
        background-color: #6c757d;
        color: white;
    } @else {
        background-color: #f8f9fa;
        color: #333;
    }
        padding: 10px 20px;
        border: none;
        border-radius: 4px;
}
```
```
.button-primary {
    @include buttonStyle('primary');
}
```

#### Nested Selector
```
//_nav.scss

@mixin navStyle($bg-color) {
    background-color: $bg-color;
    padding: 1rem;
    ul {
        list-style: none;
        display: flex;
        li {
           margin-right: 1rem;
        }
    }
}
```
```
nav {
    @include navStyle(#333);
}
```


### Using Sass
- `npm install node-sass --save-dev` - to install sass compiler `node-sass` and it will be listed in `package.json` under `devDependencies`. `devDependencies` hold the packages which are needed for local developement and testing, where as `dependencies` hold the packages which are needed in the production. To save any package under `dependencies` we use only `--save` flag.
```
"compile:sass": "node-sass sass/main.scss css/style.css -w"
```
- Add the above script in `package.json` file under `scripts` object. Here, `sass/main.scss` is the source sass file and `css/style.css` is the output file, where the pure css after compilation, will be stored. **`w`** flag is for watching, means if we run the command once, then after every time we save the changes that will be automatically compiled to destination file, we dont have to run the command each time after making some changes.
- Run `npm run compile:sass` to start using `node-sass` compiler.



## Build Process
- If we want to concat two css files, then there is one npm package called `concat`. We can install using `npm install concat`.
- `npm install autoprefixer --save-dev` We use `autoprefixer` to add prefix to modern css properties. We can pass how many latest versions of each browser, we should consider for adding prefix.
- `npm install postcss-cli --save-dev` for `autoprefixer` to work we need to install `postcss-cli`, as `autoprefixer` is part of `postcss-cli` package.
- We can compress our final css file using `node-sass` package, it will remove all the white spaces and all the comments. Generally we use this compressed version in the production because there is size difference between compressed version and uncompressed version.
- There is one npm package `npm-run-all` which we can use to run all npm scripts using one script. `npm install npm-run-all --save-dev`.
- Following is sample script for build process
```
"compile:sass": "node-sass ./sass/main.scss ./css/style.comp.css",
"concat:css": "concat -o css/style.concat.css ./css/icon-font.css ./css/style.comp.css",  // this concate multiple css files into one new css file
"prefix:css": "postcss --use autoprefixer -b 'last 5 versions' ./css/style.concat.css -o ./css/style.prefix.css",
"compress:css": "node-sass ./css/style.prefix.css ./css/style.css --output-style compressed",
"build:css": "npm-run-all compile:sass concat:css prefix:css compress:css"
```
- Following is the sample script for development workflow
```
"watch:sass": "node-sass ./sass/main.scss ./css/style.css -w",
"devserver": "live-server",
"start": "npm-run-all --parallel devserver watch:sass"  // this will run both the scripts in parallel
```
